02 · The bet

Why I picked this fight.

Four short answers to the four questions every project should be able to answer before the first commit.

Signal

Task management apps have bifurcated into two broken extremes.

Overly simple todo lists that don't help you break down complex tasks, and AI-powered tools that require internet, API keys, and subscription fees to do what a checklist could do. The gap is a middle ground: instant, offline, deterministic task breakdown.

Filter

Consumer productivity, not enterprise.

Deterministic over probabilistic — rule-based templates instead of LLMs. Offline-first as a feature, not a limitation. One-time purchase instead of subscription. Cross-platform mobile for maximum reach.

Why now

AI fatigue is real.

Users are tired of loading spinners, API rate limits, and subscription creep for simple tasks. The "AI for everything" wave has created a counter-market of people who want tools that just work — instantly, offline, forever.

Why me

I opened ChatGPT to break down "clean my apartment" and felt absurd.

A billion-parameter model burning GPU cycles to tell me to vacuum. I wanted something that just knew: say "clean", get a checklist. No tokens. No latency. No subscription. The absurdity of using a neural net for a lookup table was the catalyst.

03 · No-jargon explainer

Problem. Solution. Result.

01 · Problem

People struggle to start complex tasks because they can't see the first step.

Todo lists capture the task but don't break it down. AI-powered breakdown tools work but require internet, cost money, and sometimes hallucinate steps. The result: procrastination, overwhelm, and a feeling that productivity tools are either too dumb or too smart.

02 · Solution

Build a task-breakdown app with deterministic rule-based templates.

User says "I need to clean my room" — the app matches keywords against 8 pre-loaded templates, selects the best match using exact phrase matching and keyword density scoring, and instantly generates 4 timed subtasks. If no template matches above the 25% threshold, a wildcard fallback provides a generic 4-step structure. All processing happens on-device in under 100ms. No internet. No AI. No subscription.

08 · Exhibit
▸ Decision · deterministic beats probabilistic

When everyone else uses a neural net, we used a JSON file

The most distinctive technical decision in the app is the TemplateEngine. Every other task-breakdown tool on the market either gives you a blank list (too simple) or calls an LLM API (too heavy, too slow, too expensive, requires internet). We chose a third path: deterministic rule-based matching against a JSON template file. The algorithm has three tiers: (1) exact phrase match — if the input contains a complete keyword phrase, use that template; (2) keyword density scoring — calculate match percentage based on keyword occurrences, require minimum 25% threshold; (3) wildcard fallback — if nothing matches, use a generic 4-step template. Time estimates include a 20% buffer for transitions. The result: subtask generation in under 100ms, offline, forever, with zero tokens and zero latency.

BEFORE: LLM-powered breakdown 
// Requires internet, API key, subscription
// Latency: 500ms-3s depending on network
// Cost: $0.002 per request (adds up)
// Failure mode: network timeout, rate limit,
//   hallucination

suspend fun breakdownWithAI(task: String): List<String> {
  val response = openAI.chat.completions.create(
    model = "gpt-3.5-turbo",
    messages = listOf(
      mapOf("role" to "user",
        "content" to "Break down: $task")
    )
  )
  return parseSteps(
    response.choices[0].message.content)
}
// User waits. Server bills.
// Sometimes it makes up steps.
AFTER: deterministic template engine 
// Zero network. Zero tokens. Zero cost.
// Latency: <100ms on any device
// Failure mode: generic fallback (always works)

class TemplateEngine(
  private val templates: List<TaskTemplate>,
  private val default: DefaultTemplate
) {
  fun match(input: String): MatchedTemplate {
    val normalized = input.lowercase()
    // Tier 1: exact phrase match
    templates.forEach { t ->
      if (t.keywords.any { phrase ->
        normalized.contains(phrase) })
        return MatchedTemplate(t.subtasks, t.icon)
    }
    // Tier 2: keyword density scoring
    var best: TaskTemplate? = null
    var bestScore = 0.0
    templates.forEach { t ->
      val score = t.keywords.count { k ->
        normalized.contains(k) }.toDouble()
        / t.keywords.size
      if (score > bestScore && score >= 0.25) {
        bestScore = score
        best = t
      }
    }
    best?.let {
      return MatchedTemplate(it.subtasks, it.icon)
    }
    // Tier 3: wildcard fallback
    return MatchedTemplate(
      default.subtasks, default.icon)
  }
}
// User gets instant results.
// No server required.

Including this exhibit because the interesting part is the decision to not use AI, not the algorithm itself. The algorithm is trivial — a for-loop and some division. The decision is the story.

10 · Decisions

Five questions worth answering slowly.

Short answer first — long answer if you need it.

Q01Why no AI/ML?+

A lookup table is faster, cheaper, more reliable, and more private than a neural network for structured task breakdown. The problem doesn't require general intelligence.

Every task-breakdown request to an LLM costs money, consumes GPU resources, requires internet, and introduces latency. For the 8 most common daily tasks, a deterministic template with keyword matching produces identical or better results — instantly, offline, forever. The 20% of edge cases that don't match a template get a generic wildcard fallback that's still useful. The decision to use zero AI isn't anti-technology; it's pro-appropriateness. A hammer is the right tool for a nail, even if a hydraulic press could also do the job.

Q02Why no accounts or cloud sync?+

Accounts create friction, cloud sync creates liability, and neither is necessary for a personal task app. The user owns their data on their device.

Requiring an account drops conversion by 30-50% at the signup screen. Cloud sync requires infrastructure, GDPR compliance, breach notification procedures, and ongoing maintenance. For a personal task app used by one person on one phone, the complexity is absurd. Encrypted JSON backups provide data portability without a server. The user can AirDrop or email their backup to a new phone.

Q03Why one-time purchase instead of subscription?+

A subscription implies ongoing value creation. A task breakdown app is a utility that should work forever after purchase. Charging monthly for a JSON file feels exploitative.

The app has no server costs, no AI API costs, no ongoing infrastructure. The marginal cost of an additional user is zero. A $4.99 one-time purchase fairly compensates the development effort without creating a parasitic revenue relationship. Users hate subscription fatigue — especially for simple utilities.

Q04Why build for Android first?+

Android has broader device compatibility, lower store barriers, and a larger market for utility apps. The iOS spec is written to the same standard and will be implemented next.

Android's minSdk 26 covers 95%+ of active devices. The Play Store review process is faster than App Store review. Kotlin and Jetpack Compose are mature, well-documented, and have excellent tooling. The iOS implementation is fully spec'd in PROJECT_README.md and SecureBackupManager.swift is already implemented. The plan is Android-first to validate the product, then iOS parity.

Q05Why JSON-serialized subtasks in Room?+

Subtasks are tightly coupled to their parent task, never queried independently, and have a flexible schema. JSON serialization in a single column is simpler and faster than a join table.

A separate subtasks table with foreign keys would enable independent querying, but subtasks are never needed without their parent task. The subtask schema is simple and stable. JSON serialization via kotlinx.serialization provides type safety, easy migration, and avoids the overhead of a join query every time a task is loaded. The tradeoff is that subtasks can't be queried independently — but the app has no use case for "show me all 5-minute subtasks across all tasks."

12 · Reflection

What surprised me. What I'd do differently. What's next.

Surprised by

How strongly users reacted to the "no AI" positioning.

During early testing, the phrase "works without internet" was the single most appreciated feature — more than the widgets, more than the voice input, more than the design. People are tired of loading spinners. The deterministic engine felt like a superpower because it was instant. The 20% time buffer was also surprisingly important — users said it made the estimates feel realistic instead of optimistic.

Would do differently

Write tests from day one.

The Android codebase has zero automated tests — not unit tests, not UI tests, not integration tests. Every refactor is risky. Every edge case is discovered by a user crash. The TemplateEngine especially needs property-based testing: feed it 1,000 random task descriptions and verify it never crashes, never returns empty, and always completes in under 100ms. Testing should have been phase 2, not a future wish.

What's next

iOS parity, template marketplace, property-based testing.

iOS parity — implement the full SwiftUI stack spec'd in PROJECT_README.md. Template marketplace: sell specialized packs (camping, moving, wedding planning, home renovation). Property-based testing for TemplateEngine. Accessibility audit: screen reader support, high contrast mode, font scaling. Wear OS and Apple Watch complications for glanceable task lists. Localized templates for international markets.
